# Spec-Driven Flow — Feature Design

## Motivation

AI Dev Kit today protects code quality *after* the AI writes something (auditor) and contextualizes the session *before* it starts (CLAUDE.md). The missing layer is **intent validation**: ensuring the AI knows exactly what to build, and the developer has approved it, before a single file is touched.

Two problems this solves:

1. **Wrong output** — Claude misunderstands scope, builds too much or the wrong thing, and the developer only notices after many tokens are spent.
2. **Token waste** — large CLAUDE.md loaded every session regardless of task, generic prompts with no task-specific context, retrabalho from misalignment.

---

## Core Concept

```
developer describes task
        ↓
ai-kit spec new        → generates structured spec file
        ↓
developer reviews      → edits / approves the spec
        ↓
ai-kit spec start      → injects spec as focused context into Claude session
        ↓
Claude implements      → auditor validates each write against the spec
        ↓
ai-kit spec close      → marks spec as done, links to commit
```

The spec file is the single source of truth for a task. It replaces the need to repeat intent in every message, reduces hallucinated scope, and makes the session context much smaller and focused.

## New File Structure

```
.aikit-specs/
├── active/
│   └── SPEC-003-user-search-endpoint.md    # current in-progress spec
├── done/
│   └── SPEC-001-auth-refresh-token.md      # completed specs
│   └── SPEC-002-product-pagination.md
└── .spec-counter                           # auto-incremented ID
```

At project root (generated by `ai-kit init`, added to `.gitignore` for personal projects or committed for team use):
```
.aikit-specs/
```

## Spec File Format

Each spec is a short markdown file with a strict structure. Designed to be:
- Human-readable and editable
- Small enough to fit in a single prompt prefix (< 200 tokens ideally)
- Machine-parseable by hooks

```markdown
# SPEC-003 — User search by email endpoint

## Status
draft | approved | in-progress | done

## What
One-sentence description of the deliverable.
Example: Add GET /users/search?email= endpoint that returns paginated user list.

## Scope
- [ ] UserController: new GET /users/search endpoint
- [ ] UserService: searchByEmail(String email, Pageable pageable)
- [ ] UserRepository: findByEmailContainingIgnoreCase query
- [ ] Unit tests for service and controller layers

## Out of scope
- No changes to authentication
- No new database migrations
- No frontend changes

## Contracts
### Request
GET /users/search?email=john&page=0&size=20

### Response
UserPageDTO { users: UserSummaryDTO[], total: int, page: int }

## Stack context
- Spring Boot + JPA + Spring Security
- Existing pattern: UserController → UserService → UserRepository
- DTOs in com.example.dto, mapped with MapStruct
- Tests use @WebMvcTest and @DataJpaTest

## Files expected to change
- src/main/java/.../UserController.java
- src/main/java/.../UserService.java
- src/main/java/.../UserRepository.java
- src/main/java/.../dto/UserPageDTO.java (new)
- src/test/.../UserControllerTest.java
- src/test/.../UserServiceTest.java

## Approved by
<!-- dev signs off here before ai-kit spec start -->
```

## New Commands

### `ai-kit spec new [description]`

Generates a new spec file interactively.

**Flow:**
1. Auto-assigns next ID (reads `.aikit-specs/.spec-counter`)
2. Detects stack from existing CLAUDE.md or re-runs detect
3. Calls `claude -p` with a tight prompt: stack context + description → fills spec template
4. Opens spec file for developer review (prints path + instruction)
5. Status is set to `draft`

**Token strategy:**
- Prompt to `claude -p` is small: stack summary (30 lines max) + task description
- Does NOT pass the full CLAUDE.md — only the Architecture and Stack sections
- Output is capped: spec template has fixed sections, Claude fills them in

**Output:**
```
  OK  Spec created: .aikit-specs/active/SPEC-003-user-search-endpoint.md
  ...  Review and edit the spec, then run: ai-kit spec approve SPEC-003
```

---

### `ai-kit spec approve <id>`

Marks a spec as approved and ready to implement.

**Flow:**
1. Reads the spec file
2. Validates required sections are filled (What, Scope, Files expected)
3. Sets `Status: approved`
4. Prints a summary of what will be built

**Validation rules:**
- `## What` must not be empty
- `## Scope` must have at least one `- [ ]` item
- `## Files expected to change` must list at least one file
- `## Out of scope` must be present (even if it just says "none")

**Output:**
```
  OK  SPEC-003 approved
  ...  Scope: 4 files, 2 new, 4 tasks
  ...  Run: ai-kit spec start SPEC-003
```

---

### `ai-kit spec start <id>`

Activates a spec for the current Claude Code session.

**Flow:**
1. Validates spec status is `approved`
2. Sets `Status: in-progress`
3. Writes `.aikit-specs/.active-spec` pointing to the spec ID
4. Generates a focused `TASK.md` at project root from the spec
5. Injects TASK.md path into `.claude/settings.json` as an additional context file (if Claude Code supports it) OR prints instructions to include it

**TASK.md format** (injected as session context):
```markdown
<!-- AUTO-GENERATED — do not edit manually. Edit the spec instead. -->
# Current Task: SPEC-003

## Objective
Add GET /users/search?email= endpoint that returns paginated user list.

## Files to touch
- src/main/java/.../UserController.java
- src/main/java/.../UserService.java
- src/main/java/.../UserRepository.java
- src/main/java/.../dto/UserPageDTO.java  ← NEW
- src/test/.../UserControllerTest.java
- src/test/.../UserServiceTest.java

## Rules for this task
- Follow existing UserController pattern
- DTOs mapped with MapStruct, not manually
- All endpoints require @PreAuthorize
- Write unit test for each new method

## Out of scope — do not touch
- Authentication / security config
- Database migrations
- Frontend
```

**Token strategy:**
- TASK.md is < 50 lines — much smaller than full CLAUDE.md
- CLAUDE.md stays as background reference; TASK.md is the foreground context
- Claude reads TASK.md first (it's shorter and fresher) before reaching CLAUDE.md

**Output:**
```
  OK  SPEC-003 is now active
  OK  TASK.md written at project root
  ...  Start Claude Code — it will read TASK.md automatically
  ...  Auditor will warn if files outside the spec scope are modified
```

---

### `ai-kit spec close [id]`

Closes the active spec after implementation.

**Flow:**
1. Reads `.aikit-specs/.active-spec` (or uses provided ID)
2. Runs `git log --oneline` since spec was started — captures commit hashes
3. Marks spec `Status: done`, appends commit references
4. Moves file from `active/` to `done/`
5. Removes `TASK.md` from project root
6. Clears `.aikit-specs/.active-spec`

**Output:**
```
  OK  SPEC-003 closed
  OK  Linked to commits: abc1234 feat(user): add search endpoint
  OK  Moved to .aikit-specs/done/SPEC-003-user-search-endpoint.md
  OK  TASK.md removed
```

## Auditor Integration — Scope Guard

When a spec is active (`.aikit-specs/.active-spec` exists), the auditor gains an extra check on every `Write`:

**Out-of-scope file warning:**
- Reads `## Files expected to change` from the active spec
- If the file being written is NOT in that list AND is not a test file, logs a `LOW` finding:
  ```
  [AUDITOR] LOW — SPEC-003 scope
  File:    src/main/.../SomeOtherService.java
  Fix:     This file is not in SPEC-003's scope. Intended? Update the spec or
           add an inline suppression: // ai-kit:ignore scope
  ```

This is intentionally `LOW` (not blocking) — scope creep is common and sometimes intentional. The goal is awareness, not hard blocking.

## Token Efficiency Strategies

### 1. Sectioned CLAUDE.md

Split CLAUDE.md into loadable sections so Claude only reads what's relevant:

```
.claude/
└── context/
    ├── stack.md          # tech stack, versions — loaded always (~30 lines)
    ├── architecture.md   # folder structure, layers — loaded always (~40 lines)
    ├── rules.md          # non-negotiable rules — loaded always (~20 lines)
    ├── commands.md       # how to run/test — loaded on demand
    └── features.md       # domain features overview — loaded on demand
```

`ai-kit init` generates these files. `CLAUDE.md` becomes a short index that imports them:
```markdown
# Project Context
See: .claude/context/stack.md, architecture.md, rules.md
Active task: TASK.md (if present)
```

This way, if Claude Code supports partial context loading in the future, the infrastructure is already in place.

### 2. Prompt cache alignment

When calling `claude -p` (in spec generation, CLAUDE.md generation, smart-commit), structure prompts so the stable prefix comes first:
- System instructions (never change)
- Stack context (changes rarely)
- Task-specific content (changes every call)

This maximizes cache hits on the first two segments (5-min TTL).

Concretely: extract the system instructions for each `claude -p` call into a shared template in `hooks/lib/prompts/` so they're consistent across calls and cacheable.

### 3. Smart-commit token reduction

Currently sends the full diff to Claude. Improvement:
- For large diffs (> 200 lines), summarize per-file first, then review summaries
- Skip review for files already covered by a closed spec (trusted implementation)
- `--no-review` already exists; add `--spec-only` to review only files outside the active spec's scope

### 4. Spec-aware CLAUDE.md regeneration

`ai-kit update` today regenerates the full CLAUDE.md. With specs, it could instead update only the section that changed (e.g., if a new feature was added, append to `features.md` based on the closed spec).

## Implementation Order

Suggested sequence to minimize risk and deliver value incrementally:

1. **`ai-kit spec new` + file format** — foundation, no hooks needed
2. **`ai-kit spec approve` + validation** — enforces discipline before coding
3. **`ai-kit spec start` + TASK.md generation** — delivers the token efficiency benefit
4. **`session-start.sh` integration** — visibility into active spec
5. **Auditor scope guard** — the spec-driven enforcement layer
6. **`ai-kit spec close`** — closes the loop with commit linkage
7. **`ai-kit spec list` + `show`** — developer experience polish
8. **Sectioned CLAUDE.md** — deeper token efficiency (more structural change)
9. **Smart-commit `--spec-only`** — advanced token optimization

## Open Questions

- Should specs be committed to git? (yes for teams, optional for solo devs — controlled by `.gitignore`)
- Should `TASK.md` be auto-added to Claude Code's context files in `settings.json`, or just left at root for Claude to find naturally?
- Should `ai-kit spec new` block if another spec is already `in-progress`? (probably warn, not block)
- Should the auditor scope guard be opt-in via `.aikit-rules.yml` or always-on when a spec is active?
